1. 数据结构改造
conversations 表
sql
CREATE TABLE conversations (
  id BIGINT PRIMARY KEY,
  user_id BIGINT,
  summary TEXT,                         -- 历史摘要
  summary_last_message_id BIGINT DEFAULT 0, -- 已纳入摘要的最后一条消息ID
  summary_updated_at DATETIME,
  created_at DATETIME,
  updated_at DATETIME
);
messages 表
建议加一个 turn_index，因为一轮对话不一定只有 2 条消息，可能还有工具调用、检索结果等。

sql
CREATE TABLE messages (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  conversation_id BIGINT,
  turn_index INT,                       -- 第几轮对话
  role VARCHAR(20),                     -- user / assistant / system / tool
  content TEXT,
  token_count INT,
  created_at DATETIME
);
用户发一条新消息时：

text
turn_index = 当前会话最大 turn_index + 1
assistant 回复时沿用同一个 turn_index。

2. 每轮对话的处理流程
收到用户新问题后：

保存用户消息，分配 turn_index。

读取当前会话的 summary 和 summary_last_message_id。

取最近 2 轮完整原文。

找出“已摘要指针之后、最近 2 轮之前”的消息。

如果这些消息达到摘要阈值，就调用摘要模型做增量摘要。

更新 conversations.summary 和 summary_last_message_id。

用当前问题 + 摘要 + 最近原文改写检索 query，去知识库检索。

拼装最终 messages，调用主模型。

保存 assistant 回复。

3. 关键：增量摘要，而不是全量摘要
假设保留最近 2 轮原文。

当前会话：

text
第1轮：user / assistant
第2轮：user / assistant
第3轮：user / assistant
第4轮：user / assistant
第5轮：用户刚发新问题
你保留最近 2 轮，也就是第3、4轮原文。
那么第1、2轮就进入摘要。

下次第6轮来了：

text
已摘要：第1、2轮
最近原文：第4、5轮
待摘要：第3轮
于是把旧摘要 + 第3轮，合并成新摘要。

这样不会每轮重摘全部历史，成本低，也不会丢早期上下文。

4. 拼装顺序
最终传给大模型的结构建议：

text
system: 你是知识库助手，以下是检索到的资料...
system: 历史对话摘要：...
user/assistant: 最近第1轮完整原文
user/assistant: 最近第2轮完整原文
user: 当前问题
如果有些旧消息还没达到摘要阈值，也可以临时放在摘要和最近原文之间：

text
system: 基础提示 + 知识库检索结果
system: 历史摘要
user/assistant: 未摘要旧原文
user/assistant: 最近2轮原文
user: 当前问题
但未摘要旧原文要限制 token，超过阈值就强制摘要。

5. 伪代码示例
python
RECENT_TURNS = 2
SUMMARY_TRIGGER_TOKENS = 800

def build_context(conv_id, current_question, current_msg_id):
    conv = load_conversation(conv_id)

    # 1. 取最近 2 轮完整原文，不包含当前问题
    recent_msgs = load_recent_turns(
        conv_id=conv_id,
        before_msg_id=current_msg_id,
        turns=RECENT_TURNS
    )

    recent_min_turn = min(m.turn_index for m in recent_msgs) if recent_msgs else 999999

    # 2. 找待摘要消息：已摘要指针之后，最近原文之前
    pending_msgs = load_messages(
        conv_id=conv_id,
        after_id=conv.summary_last_message_id,
        before_turn=recent_min_turn,
        roles=["user", "assistant"]
    )

    # 3. 判断是否需要更新摘要
    pending_tokens = sum(m.token_count for m in pending_msgs)

    if pending_msgs and pending_tokens >= SUMMARY_TRIGGER_TOKENS:
        new_summary = call_summary_model(
            old_summary=conv.summary,
            new_messages=pending_msgs
        )

        update_conversation_summary(
            conv_id=conv_id,
            summary=new_summary,
            last_message_id=pending_msgs[-1].id
        )

        conv.summary = new_summary
        pending_msgs = []

    # 4. 知识库检索：query 最好结合摘要和最近原文改写
    retrieval_query = rewrite_query(
        current_question=current_question,
        summary=conv.summary,
        recent_msgs=recent_msgs
    )
    docs = retrieve_knowledge(retrieval_query)

    # 5. 拼 messages
    system_content = build_system_prompt(docs)

    messages = [
        {"role": "system", "content": system_content}
    ]

    if conv.summary:
        messages.append({
            "role": "system",
            "content": f"历史对话摘要：\n{conv.summary}"
        })

    # 未达到摘要阈值的旧原文，临时带上，避免丢信息
    for m in pending_msgs:
        messages.append({"role": m.role, "content": m.content})

    # 最近 1-2 轮完整原文
    for m in recent_msgs:
        messages.append({"role": m.role, "content": m.content})

    # 当前问题
    messages.append({"role": "user", "content": current_question})

    return messages
6. 摘要提示词模板
摘要模型可以单独用一个小模型，成本低。

text
你是对话摘要器。请把“已有摘要”和“新增对话”合并成更新后的摘要。

要求：
1. 只保留对后续回答有用的信息。
2. 重点保留：用户目标、背景、约束、偏好、已确认事实、未解决问题、重要实体、数字、时间、代码、ID。
3. 不要编造，不要加入对话中不存在的信息。
4. 如果新信息与旧摘要冲突，以新对话为准。
5. 删除寒暄、重复、无关内容。
6. 用简洁要点输出，不超过 600 tokens。

新增对话：

7. 知识库检索要注意
摘要不能替代知识库检索。每轮仍然要根据当前问题检索。

但检索 query 不能只用当前问题，因为用户可能说：

text
“它怎么配置？”
“那第二个方案呢？”
“这个报错怎么解决？”
所以检索前最好做 query 改写：

text
当前问题 + 最近一轮用户问题 + 摘要中的关键实体
例如摘要里有“用户在配置 Nginx 反向代理”，当前问“它怎么配置 HTTPS？”，检索 query 应改写成：

text
Nginx 反向代理 HTTPS 配置
检索结果放在 system 中，和对话摘要分开：

text
[系统提示]
[知识库检索资料]
[历史对话摘要]
[最近原文]
[当前问题]
8. 推荐参数
项目	建议
最近原文	1-2 轮
摘要触发	待摘要 token > 800 或待摘要轮数 >= 2
摘要长度	400-800 tokens
摘要模型	小模型，低成本
知识库 topK	根据 token 动态调整
总上下文	摘要 15%，最近原文 25%，知识 40%，当前问题 10%
9. 注意事项
摘要要增量更新，不要每次把全部历史重新摘要。

保留最近原文，因为最近 1-2 轮往往包含代词、指代、用户纠正，摘要容易丢细节。

重要 ID、代码、URL、数字尽量原文保留，不要只靠摘要。

同一会话摘要更新要加锁，避免并发重复摘要。

多分支会话要加 branch_id，否则编辑重生成会污染摘要。

异步摘要可以降低主请求延迟：上一轮回复完成后异步更新摘要，下一轮使用。

如果摘要未及时更新，拼装时把未摘要旧原文临时带上，避免信息丢失。
