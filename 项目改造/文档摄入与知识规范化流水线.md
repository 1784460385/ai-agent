正式架构描述
用户上传文件后，系统不直接把原始文件作为检索对象，而是先经过一条文档摄入与知识规范化流水线：
格式识别 → 内容解析 → 清洗去噪 → 结构还原 → 统一为规范化文档 → 语义分块 → 元数据抽取 → 写入知识库并建立索引。

不同格式的文件，如 PDF、Word、Excel、PPT、HTML、Markdown、TXT，最终都被转换成同一种可检索、可引用、可向量化的知识表示。后续关键词检索、BM25 检索和向量检索都面向规范化后的知识单元，原始文件仅保留用于溯源和重新解析。

处理流程可以这样描述
上传接收
保存原始文件，记录 user_id、doc_id、folder_id、文件名、类型、大小、上传时间。

格式识别与解析

PDF：抽取文本、页码、版面信息

Word：抽取段落、标题、表格

Excel：表格转 Markdown / CSV

PPT：逐页抽取文本和备注

HTML：抽取正文，去导航广告

Markdown / TXT：直接读取

清洗与去噪
去掉页眉页脚、水印、乱码、重复空行、无意义符号。

结构还原
保留标题层级、列表、表格、代码块、章节路径、页码等结构。

统一规范化输出
转成两种中间表示：

Markdown：保留人类可读结构，适合展示和溯源

JSONL：每行一个知识单元，适合入库和检索

语义分块
按标题、段落、表格、列表切分，而不是固定 500 字硬切。块之间保留一定重叠。

元数据抽取
每个知识单元带：

json
{
  "chunk_id": "...",
  "user_id": "...",
  "doc_id": "...",
  "folder_id": "...",
  "source": "技术部/Nginx配置.md",
  "page": 3,
  "heading_path": ["Nginx", "HTTPS 配置"],
  "content": "……",
  "content_type": "text",
  "parser_version": "v1"
}
写入知识库并建索引

SQLite：存原始文件、解析结果、知识单元

SQLite FTS5：建全文索引，供关键词检索

ChromaDB：存向量，供语义检索

存储分层可以这样描述
建议把知识库分成四层：

层级	作用	存什么
原始文件层	溯源、重新解析	用户上传的 PDF、Word、Excel 等
规范化文档层	统一格式	解析后的 Markdown / JSON
知识单元层	检索基本单位	分块后的 chunk + 元数据
索引层	加速检索	FTS5 全文索引、Chroma 向量索引
后续关键词检索时，不是去扫原始文件，也不是扫整个 JSON，而是查 知识单元层 + 全文索引。
例如 SQLite 里建一个 knowledge_chunks_fts 虚拟表，用 MATCH 查询，返回 chunk_id，再关联 knowledge_chunks 取原文和来源。

可直接放进架构说明的段落
系统在知识库中增加一个文档摄入与知识规范化层。用户上传文件后，系统先进行格式识别、内容解析、清洗去噪和结构还原，将 PDF、Word、Excel、PPT、HTML、Markdown、TXT 等异构文件统一转换为 AI-ready 的规范化文档，再按语义结构切分为知识单元，并抽取来源、页码、章节路径等元数据。规范化后的知识单元写入数据库，并分别建立全文索引和向量索引。后续关键词检索、BM25 检索和向量检索均面向规范化知识单元，原始文件仅用于溯源和重新解析。这样不同格式的文件最终都变成同一种可检索、可引用、可向量化的知识表示。

需要注意的一点
“AI 易于理解的格式”是产品语言，技术描述最好说成：

机器可读、结构统一、语义完整、可检索、可溯源的知识表示。

另外，如果你说的“关键词检索直接从这个转化后的知识库读取内容”，底层最好用 SQLite FTS5 或类似全文索引，而不是用 LIKE 扫表。否则数据一多，关键词检索会变慢，也发挥不出规范化知识库的优势。
