1. 背景与目标
现状：当前 API Key 在聊天界面左下角临时输入，且“只随本次提问发送，后端不保存”，导致用户每次登录、刷新页面都需要重新输入，且无法管理多套配置。
目标：将 API Key 的管理从聊天会话中剥离，建立独立的用户级配置页面。实现多 Key 持久化存储、随时切换、且绑定当前系统账号。

2. 功能需求详述
2.1 页面与入口

移除旧入口：隐藏或移除聊天页面左下角的 API Key 输入悬浮窗。

新增独立页面：新增“API 设置”或“模型配置”页面。

页面入口：建议放置在右上角用户头像下拉菜单中（或左侧导航栏“用户管理”同级）。

2.2 API Key 管理（增删改查）

新增配置：用户可添加多个 API Key，每个配置包含：

别名/名称（例如：“DeepSeek 生产号”、“DeepSeek 测试号”）

API Key 字符串

模型名称（如 deepseek-chat, deepseek-flash，可绑定或动态选择）

Base URL（可选，视你是否支持代理或第三方兼容接口而定）

列表展示：展示已保存的 Key 列表。

安全要求：列表不得完整显示明文，必须脱敏处理（如：sk-xxxx********xxxx）。

操作：支持编辑、删除、设为默认。

持久化要求：保存后与当前系统用户 ID 绑定，写入数据库。用户下次登录时，自动拉取并展示这些配置。

2.3 切换与使用

默认 Key：用户可设置某一个 Key 为“默认”。

聊天页面切换：在聊天界面的输入框上方或顶部状态栏，提供一个下拉选择器，可以快速切换当前对话使用哪一个 API Key。

生效机制：用户在聊天界面选择某个 Key 时，该会话（或当前用户默认）直接使用该 Key 发起请求，无需再次输入。

3. 安全与权限要求（非常重要）
加密存储：后端数据库存储 API Key 时，必须进行 对称加密（如 AES）后再落库，绝不能明文存储。

返回脱敏：接口返回给前端的 Key 必须是脱敏后的（如隐藏中间部分），修改和删除需通过 ID 操作，前端不存储完整明文。

权限隔离：用户只能查看和操作自己账号下的 API Key，严禁跨用户读取。

调用隔离：后端在发起大模型请求时，从数据库解密对应的 Key，确保“只用当前用户自己配置的 Key 计费”。

4. 交互建议（前端 UI/UX）
页面布局：类似于“表格+弹窗”的形式。列表显示已有的 Key，右上角有“新增 Key”按钮。

聊天页面的变化：左下角原有的输入框区域可以改为显示当前使用的 Key 名称（如“当前模型：DeepSeek 默认配置”），点击可直接跳转到 API 设置页面，或者弹出一个轻量级的切换抽屉。

异常处理：如果用户未配置任何 API Key，聊天输入框应处于禁用状态，并提示“请先前往个人中心配置 API Key”。

5. 后端技术要点（提示开发/自己落地）
新增表 user_api_keys，字段建议包含：id, user_id, name, api_key_encrypted, model, base_url, is_default, created_at。

修改聊天接口：接收 api_key_id 参数，而不是直接接收明文的 api_key。

增加 API 接口：GET /api/keys（列表）、POST /api/keys（新增）、PUT /api/keys/{id}（更新）、DELETE /api/keys/{id}（删除）、POST /api/keys/{id}/default（设为默认）。
